# ResNetEngine — Native RK3576 Feature Extraction

`ResNetEngine` is the native C++ inference engine used by the NanoPi video-processing workflow. It loads a fixed-batch ResNet50V2 RKNN feature-extractor model, preprocesses JPEG images with Rockchip MPP and RGA, and runs multi-batch inference through the RKNN Runtime.

The engine is implemented as a standalone shared C++ library. The Python module is a thin pybind11 extension linked to that library; the same shared library is also used by the native benchmark executable.

For the user-facing video workflow, start with the repository's [main README](../../README.md). This document covers the engine implementation, build process, and programming interfaces.

## Architecture overview

The standard image-processing path is:

```text
JPEG file
   │
   ▼
Read JPEG bytes
   │
   ▼
Rockchip MPP MJPEG decoder
   │  NV12 / YUV420SP frame in a DMA-BUF
   ▼
Rockchip RGA
   │  NV12 → RGB888 (BT.601 full range)
   ▼
ResNet50V2 preprocessing
   │  RGB value / 127.5 - 1.0
   │  FP16 conversion
   ▼
RKNN Zero-Copy input memory
   │
   ▼
RKNN Runtime — fixed-batch NPU inference
   │
   ▼
RKNN Zero-Copy output memory (FP16)
   │
   ▼
Convert feature values to float32
   │
   ▼
Feature vectors: [number_of_images, 2048]
```

### JPEG decode and preprocessing

1. The engine reads the JPEG file into memory and copies its compressed bytes into an MPP DMA-BUF input buffer.
2. Rockchip MPP decodes the JPEG using the hardware MJPEG decoder and returns an NV12 (`MPP_FMT_YUV420SP`) frame.
3. RGA converts NV12 to RGB888 using the BT.601 full-range conversion.
4. A precomputed lookup table applies the ResNet50V2 normalization formula to each RGB channel:

   ```text
   normalized = pixel / 127.5 - 1.0
   ```

   Each normalized value is rounded to IEEE FP16.
5. The normalized FP16 tensor is written directly into the RKNN Zero-Copy input buffer. There is no separate final input tensor followed by an additional copy into the RKNN input allocation.

The MPP decoder and its buffers, the RGA configuration, the RGB working buffer, and the normalization lookup table are reused across images. The MPP/RGA preprocessor is initialized lazily when the first JPEG is processed.

### RKNN Zero-Copy inference

During initialization, the engine:

- Loads the RKNN model and initializes an RKNN Runtime context.
- Queries the native input/output tensor attributes from the runtime.
- Allocates input and output memory with `rknn_create_mem()`.
- Binds those allocations with `rknn_set_io_mem()`.
- Synchronizes the input memory to the device, calls `rknn_run()`, and synchronizes the output memory back to the CPU for reading.

The input preprocessing stage writes directly to the RKNN input allocation. The output tensor is native FP16 and is converted to float32 before the feature vectors are returned to C++ or Python.

## RKNN model contract

The feature-extractor models generated by this project use a fixed batch dimension. Their native RKNN tensor contract is:

| Tensor | Required native format |
|---|---|
| Input | FLOAT16, NHWC, `[batch, 180, 320, 3]` |
| Output | FLOAT16, `[batch, 2048]` |

The current project model uses 320x180 RGB input and returns 2048 pooled ResNet50V2 features per image.

At initialization, the C++ engine queries the model through RKNN Runtime and validates the actual tensor metadata. It checks that the model has one input and one output; that the input is four-dimensional FLOAT16 NHWC with three channels; that the input batch matches the requested batch; that the output is two-dimensional FLOAT16 with the same batch; and that the expected buffer sizes are contiguous and have no unsupported padding/stride. It does not trust the filename as proof of the model's internal shape.

The engine also requires non-zero even input width and height. The JPEG preprocessor rejects an image whose dimensions do not exactly match the loaded model. It does not resize images. The model distributed for this project expects 320x180 JPEGs.

## Fixed-batch operation

Supported batch sizes are:

- `1`
- Any positive even integer: `2`, `4`, `6`, `8`, and so on.

Each RKNN file is compiled for one fixed batch size. The model and the `batch_size` passed to `ResNetEngine` must match. The engine checks the actual model metadata at startup and fails if the requested batch does not match it.

For batch sizes greater than 1, the engine calls `rknn_set_batch_core_num()` with the requested NPU core count. The RK3576 implementation accepts 1 or 2 NPU cores; the default is 2. The core-count setting is not applied for batch 1.

If the number of remaining images is smaller than a complete batch, the engine copies the last valid sample into the unused batch slots, executes the fixed-size RKNN batch, and discards the padded outputs. This keeps the model input shape fixed without returning duplicate feature vectors.

### Model filenames

Batch 1 retains the original filename without a suffix. Larger variants use `_batchN`:

```text
resnet50v2_feature_extractor_rk3576_fp16_320x180.rknn
resnet50v2_feature_extractor_rk3576_fp16_320x180_batch2.rknn
resnet50v2_feature_extractor_rk3576_fp16_320x180_batch4.rknn
resnet50v2_feature_extractor_rk3576_fp16_320x180_batch8.rknn
```

In the main Python workflow, `--batch-size` defaults to 4 and selects the corresponding filename. When `--extractor` is supplied explicitly, its filename determines the effective batch size; a filename without `_batchN` is interpreted as batch 1. See the main README for the complete user-facing command behavior.

## Build requirements

Build and run the engine on the 64-bit ARM NanoPi system. The build requires:

- A working RK3576 NPU driver and RKNN Runtime compatible with the board image.
- RKNN Runtime headers and AArch64 `librknnrt.so` in `nanopi/resnet_engine/librknn_api/`.
- Rockchip MPP and RGA development headers and libraries, including their `pkg-config` files. The default prefix is `/opt/rkmpp-stack`.
- `g++` with C++17 support, `pkg-config`, `ldd`, and `realpath`.
- Python 3.12 environment from `nanopi/.venv-resnet/`, with pybind11 installed, for the Python extension.

The NanoPi setup script `nanopi/setup-venv-resnet.sh` installs pybind11. RKNN Toolkit2 is **not** needed on the NanoPi to run inference. RKNN Toolkit2 2.3.2 is used by the optional PC/WSL conversion workflow; the NanoPi engine links directly to the RKNN Runtime library.

## Building the engine

Run the following commands from the repository's `nanopi/resnet_engine` directory.

### 1. Download the RKNN Runtime SDK files

```bash
./get-rknn-lib.sh
```

The script sparse-clones the upstream [`airockchip/rknn-toolkit2`](https://github.com/airockchip/rknn-toolkit2) repository at tag `v2.3.2` and copies only:

- `rknpu2/runtime/Linux/librknn_api/include/`
- `rknpu2/runtime/Linux/librknn_api/aarch64/`

into `nanopi/resnet_engine/librknn_api/`.

> **Important:** the script replaces the local `librknn_api/` directory before installing the downloaded copy. Back up any local modifications there before running it again. This directory is ignored by Git.

### 2. Build the standalone C++ shared library

```bash
./src/build-resnet-engine-library.sh
```

The output is:

```text
nanopi/resnet_engine/lib/libresnet_engine.so
```

The build links the engine against `librknnrt`, Rockchip MPP, RGA, and pthreads. The default MPP/RGA installation prefix is `/opt/rkmpp-stack`. For a non-default prefix, set `RKMPP_PREFIX` for this build:

```bash
RKMPP_PREFIX=/path/to/rkmpp-stack ./src/build-resnet-engine-library.sh
```

The script checks the runtime dependencies with `ldd` and verifies that RKNN Runtime, MPP, and RGA resolve from the expected locations.

### 3. Build the Python extension

Activate the NanoPi Python environment and build the pybind11 module against the shared library:

```bash
source ../.venv-resnet/bin/activate
./src/build-resnet-engine-python-ext.sh
```

The extension is written to:

```text
nanopi/resnet_engine/python/resnet_engine<python-extension-suffix>
```

The build script uses the selected Python interpreter to obtain the Python and pybind11 include flags and the correct extension suffix. It also checks that the extension resolves `libresnet_engine.so` from this project directory.

### 4. Optional: build the native benchmark

```bash
./src/build-resnet-engine-benchmark.sh
```

This creates:

```text
nanopi/resnet_engine/resnet-engine-benchmark
```

The benchmark links to the same `libresnet_engine.so` used by the Python extension.

### 5. Optional: build the MPP/RGA JPEG diagnostic utility

```bash
./src/build-rkmpp-jpeg-decode.sh
```

This creates `nanopi/resnet_engine/rkmpp-jpeg-decode`. It uses the `/opt/rkmpp-stack` MPP/RGA installation and requires the zlib development package (`zlib1g-dev`). Unlike the shared-library build script, its current build script uses the fixed `/opt/rkmpp-stack` prefix.

## Python API

The extension module is named `resnet_engine`. The main public class is `ResNetEngine`.

### Initialize and inspect the engine

```python
from pathlib import Path
import sys

sys.path.insert(0, str(Path("resnet_engine/python").resolve()))
import resnet_engine

model_path = "../resnet/models/resnet50v2_feature_extractor_rk3576_fp16_320x180_batch4.rknn"

with resnet_engine.ResNetEngine(
    model_path,
    batch_size=4,
    npu_core_count=2,
) as engine:
    print(engine.info)
```

`engine.info` exposes:

- `batch_size`
- `input_width`, `input_height`, and `input_channels`
- `feature_count`
- `npu_core_count`
- `runtime_api_version`
- `driver_version`

The engine also exposes the read-only `model_path` and `closed` properties. `close()` releases RKNN, MPP, and RGA resources and is safe to call more than once. The object can be used as a context manager.

### Stream features from a folder

```python
stream = engine.process_folder(
    "/path/to/320x180/jpeg_images",
    chunk_size=64,
    recursive=False,
)

try:
    for image_paths, features in stream:
        # features is a float32 NumPy array with shape [len(image_paths), 2048]
        print(len(image_paths), features.shape)

    print(stream.stats)
finally:
    stream.close()
```

`process_folder()` discovers JPEG images and processes them lazily. Paths are sorted lexicographically. Set `recursive=True` to include subdirectories. The returned `FeatureStream` yields `(image_paths, features)` pairs, where each feature matrix is row-major float32 with shape `[number_of_images_in_chunk, feature_count]`.

### Process an explicit list of files

```python
image_paths = [
    "/path/to/frame_001.jpg",
    "/path/to/frame_002.jpg",
]

stream = engine.process_files(image_paths, chunk_size=64)
for paths, features in stream:
    print(paths, features.shape)
```

`process_files()` preserves the order of the supplied paths. It accepts an iterable of path-like objects, not a single string.

### Chunk size versus inference batch size

`chunk_size` controls how many processed images are grouped into each Python/C++ stream result. It is **not** the RKNN batch size. The engine can execute several fixed-size RKNN batches while filling one returned chunk.

For example, with `batch_size=4` and `chunk_size=64`, the engine normally performs 16 RKNN inference calls before yielding a 64-image result chunk.

### Stream statistics

The Python `stream.stats` dictionary contains:

- `files_found`
- `images_processed`
- `images_failed`
- `batches_executed`
- `features_returned`
- `completed`
- `closed_early`
- `failures` — a list of dictionaries with `path` and `reason` for images that could not be processed.

Image-specific failures, such as unreadable or incorrectly sized JPEGs, are recorded and skipped so the rest of the stream can continue. Engine/runtime failures raise an exception. The C++ `StreamStats` structure also contains aggregate stage timings and per-batch timings; these timing fields are not currently included in the Python dictionary.

### Infer already-preprocessed tensors

`infer_preprocessed()` bypasses JPEG decoding and RGA preprocessing. It accepts a four-dimensional float32 NumPy array containing ResNet50V2-normalized values in the `[-1, 1]` range, in either NCHW or NHWC layout:

```python
import numpy as np

# Example input shape: [N, 3, 180, 320], NCHW
normalized_images = np.zeros((5, 3, 180, 320), dtype=np.float32)
features = engine.infer_preprocessed(normalized_images)

# Result shape: [5, 2048], float32
print(features.shape, features.dtype)
```

The layout is inferred from the tensor shape and must match the loaded model dimensions. The engine converts the values to native FP16 NHWC, splits arbitrary sample counts into fixed-size RKNN batches, pads an incomplete final batch, and discards the padded outputs.

The pybind11 bindings release the Python GIL around the long-running native processing and inference calls.

## C++ API

The public header is:

```text
nanopi/resnet_engine/include/resnet_engine.h
```

The shared library is:

```text
nanopi/resnet_engine/lib/libresnet_engine.so
```

The main API is in namespace `resnet_npu`:

- `ResNetEngine(model_path, batch_size = 4, npu_core_count = 2)`
- `info()`, `model_path()`, `is_closed()`, and `close()`
- `process_folder(folder_path, chunk_size = 64, recursive = false)`
- `process_files(image_paths, chunk_size = 64)`
- `infer_preprocessed(tensor, sample_count, layout)`
- `FeatureStream::next()`, `close()`, and `stats()`

The engine uses `shared_from_this()` when creating feature streams, so C++ applications should own it through `std::shared_ptr<ResNetEngine>` rather than a stack-allocated `ResNetEngine` object.

A minimal C++ example:

```cpp
#include "resnet_engine.h"

#include <iostream>
#include <memory>

int main() {
    using namespace resnet_npu;

    auto engine = std::make_shared<ResNetEngine>(
        "../../resnet/models/resnet50v2_feature_extractor_rk3576_fp16_320x180_batch4.rknn",
        4,
        2);

    std::cout << engine->info().feature_count << " features per image\n";

    auto stream = engine->process_folder("../../resnet/dataset/andreea-esca", 64, false);
    FeatureChunk chunk;
    while (stream->next(chunk)) {
        std::cout << chunk.image_paths.size() << " images; "
                  << chunk.features.size() << " feature values\n";
    }

    const StreamStats stats = stream->stats();
    std::cout << stats.images_processed << " images processed\n";
    engine->close();
    return 0;
}
```

`FeatureChunk::features` is a row-major `std::vector<float>` containing `[image_paths.size(), feature_count]` values. The C++ `StreamStats` structure contains the same counters exposed by Python, plus aggregate `StreamTimings` and a `BatchTiming` record for each executed inference call.

Applications linking the shared library must also be able to resolve `librknnrt.so`, `librockchip_mpp.so`, and `librga.so`. The built library includes runtime search paths for the repository-local RKNN SDK and the configured MPP/RGA prefix.

## Native performance benchmark

Build the benchmark as described above, then run it from the engine directory:

```bash
cd resnet_engine
./resnet-engine-benchmark
```

The default model and image-directory paths are resolved relative to the executable location, not the current working directory:

- Model: `../../resnet/models/resnet50v2_feature_extractor_rk3576_fp16_320x180_batch4.rknn`
- Images: `../../resnet/dataset/andreea-esca`

Options:

| Option | Default | Purpose |
|---|---:|---|
| `--model PATH` | Batch-4 model above | RKNN model file. |
| `--batch-size N` | `4` | Fixed batch size; must match the model. Accepts 1 or a positive even integer. |
| `--images-dir PATH` | Dataset class folder above | Directory with JPEG images. Only top-level `.jpg`/`.jpeg` files are scanned. |
| `--used-images N` | `256` | Requested number of measured images, excluding the warm-up files. |
| `--warm-target N` | `16` | Target number of warm-up samples, rounded up to complete batches. |

The first two sorted JPEG files are reserved for warm-up and are never included in the measured workload. The benchmark repeats this A/B pair to fill the warm-up batches. If the requested measured image count is not divisible by the batch size, the incomplete tail is skipped rather than padded. The benchmark requires native 320x180 JPEG files and does not resize them.

The report separates:

- JPEG load and preprocessing, including file read, JPEG copy to the MPP DMA-BUF, MPP decode, RGA conversion, and normalization/FP16 conversion.
- Input cache synchronization, `rknn_run()`, output cache synchronization, and output reading.
- Inference-only timing, excluding preprocessing and file I/O.
- End-to-end timing, including disk reads and the complete JPEG-to-feature pipeline.

Model loading, RKNN initialization, MPP/RGA initialization, directory scanning, and warm-up are excluded from the measured workload. The benchmark calls the same `libresnet_engine.so` as the Python extension.

When using a non-default model, pass a matching `--batch-size` as well as `--model`. The standalone benchmark is a low-level diagnostic tool and does not perform the model-selection convenience logic used by the main Python workflow.

## MPP/RGA JPEG diagnostic utility

The optional `rkmpp-jpeg-decode` program runs one JPEG through the same MPP decode, RGA color conversion, ResNet50V2 normalization, and FP16 rounding stages, then writes a PNG in the current directory. This is useful for checking the preprocessing result independently of RKNN inference.

Build it with:

```bash
./src/build-rkmpp-jpeg-decode.sh
```

Run it with a 320x180 JPEG:

```bash
./rkmpp-jpeg-decode /path/to/frame.jpg
```

The output is written to the current directory using the input filename stem with a `.png` extension. The utility intentionally accepts only 320x180 JPEGs. Its build requires MPP/RGA development files under `/opt/rkmpp-stack` and `zlib1g-dev`.

## Generated files and troubleshooting

The following paths are generated locally and ignored by Git:

- `librknn_api/` — downloaded RKNN Runtime headers and AArch64 library.
- `lib/` — `libresnet_engine.so`.
- `python/` — the compiled pybind11 extension.
- `resnet-engine-benchmark` — optional benchmark executable.
- `rkmpp-jpeg-decode` — optional JPEG diagnostic executable.

Common checks:

- **Python cannot import `resnet_engine`:** confirm the extension was built with the active `.venv-resnet` interpreter and that `nanopi/resnet_engine/python/` is the directory being imported.
- **The extension cannot load `libresnet_engine.so`:** rebuild the shared library first, then rebuild the Python extension. The build scripts use `ldd` to verify the expected local library resolution.
- **RKNN Runtime or MPP/RGA library is not found:** check the paths under `nanopi/resnet_engine/librknn_api/aarch64/` and `/opt/rkmpp-stack/lib/`, and inspect the built library with `ldd`.
- **The engine rejects the model batch:** use the model variant whose fixed batch matches the constructor argument. The engine independently checks the native RKNN tensor dimensions and types; renaming a model file does not change its compiled batch.
- **The engine skips a JPEG:** check that the file is a valid JPEG and its dimensions exactly match the model input. The project feature extractor expects 320x180 images.

For the complete video-processing workflow and model-conversion procedure, see the [main project README](../../README.md).
